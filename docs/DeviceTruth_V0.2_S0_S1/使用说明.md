## 2. 推荐执行顺序

1. 首先将本包放到仓库，**保留旧 V0.1 文档和源码**。
2. 执行 **M0 基线审计与契约冻结**：在同一连续工作周期中先完成原 R01 的只读事实核对、填写 `S0_AUDIT.md`，再依据这些事实完成原 R02 的规格修订；禁止跳过审计直接改规格。Codex 独立 Review，写 `reviews/M0.md`，通过后才将 `spec.md` 冻结。
3. 执行 **M1 HTTP 接入层**：合并原 R03/R04，实现双 Main、Catalog、Session 和四类 Router；运行相关测试和关键 CLI 回归后，由 Codex 写 `reviews/M1.md`。
4. 执行 **M2 查询与 Core 请求适配**：完成原 R05 的 QUERY 闭环和 Goal→DiagnosisRequest 映射；由 Codex 写 `reviews/M2.md`。
5. 执行 **M3 异步诊断与最终验收**：连续完成原 R06/R07；内部先验证运行状态机，再验证结果/事件和 TC-01~TC-20，最终由 Codex 写 `reviews/M3.md`。

> M0 的事实审计和契约冻结逻辑上仍严格先后，但不再为两者重复创建会话和 Review。开发者与 Reviewer 必须使用独立上下文；独立性来自真实 diff、测试证据和固定基线，不依赖特定模型品牌。

## 3. 单个里程碑标准流程

`读取项目状态 → 确定里程碑 ID → 只做当前里程碑 → 实际运行分层测试 → 交付摘要 → Codex 独立 Review → 修复/复审 → 通过后更新状态并建立 checkpoint → 进入下一里程碑`

- 开发者：改源码 / 写测试 / 运行命令。M0 只写审计和规格文档，**不进行业务编码**；M1~M3 才编码。
- Codex Reviewer：原则上**不改源码和测试**，只新建 `reviews/Mx.md` 并给出结论。PASS 后由交接步骤统一维护 `state.md/task.md`；涉及 `spec.md` 变化须得到用户批准并有证据。
- 用户：决定重大架构分歧；不让两个模型自行“改出第三套方案”。
- 里程碑通过条件：当前验收点有真实测试证据，Codex 没有未解决的 P0/P1，强制离线基线未退化。JDK、编译、离线测试、打包和 scripted CLI 阻塞时必须标 `BLOCKED`；仅在线 Key/网络/额度可单独标 `BLOCKED_BY_ENV` 而不冒充在线 PASS。

### Git 规范

- 在 S0 首先记录原始 `git status`、当前分支与基线 commit；不得 `reset --hard`/`clean -fd` 或覆盖未跟踪文件。
- 不假设仓库已有干净工作树。Review 比较“本轮开始基线 → 本轮交付修改”，而不是无差别扫描所有历史改动。
- 没有明确授权时，模型不得创建 commit、tag、push、改远程分支。可以提出建议，交由用户决定。
- 每个里程碑 PASS 后应在用户授权下建立本地 checkpoint commit；下一里程碑以该 commit 为基线。若不授权 commit，必须保存完整基线补丁和文件哈希，不能只记录“工作树为脏”。
- 中间 Review 只检查当前里程碑 diff、关键调用链及关联测试；M3 做全量集成复核，不要求每次重读全仓库。

## 4. 优质生成/迭代方式

**不要一次性让模型读修订方案就直接生成所有代码。** 最稳妥的方式是本包作为 v0，按以下闭环迭代：

1. **设计规格来自方案**：预先明确 S0/S1 边界、契约、依赖和测试点。
2. **源码事实来自 M0 前半段**：把方案中“据历史审查”的描述逐一核查，引用实际类/方法/文件和测试结果。
3. **契约冻结来自 M0 后半段**：只能依据前半段事实修订，Codex 一次性把关审计可追溯性和规格可实施性。
4. **代码按三个里程碑推进**：M1 接入层、M2 查询与映射、M3 异步诊断和验收；不扩大到 S2/S3/S4。
5. **Review 必须来自代码和实际测试**：不能只依赖开发者的工作摘要或自述通过数量。

这样生成的包质量会明显高于“让 AI 一口气规划、写代码、验收并自行宣布完成”。

## 5. 关键边界（不得混淆）

- `CAR-B / COMM_TIMEOUT` 是**汽车演示数据**，**不是**工业 `SC-0245-B`。
- CLI 的真实场景为 **A/B/C/D**；E 是负例测试，不是 `--scenario=E`。
- 旧文档中的“42 项通过”不能自动当作当前验收；2026-11-08 的流程合并预检虽重新得到 42/42 PASS，M0 仍须记录完整命令、环境和 CLI/打包证据。
- `diagnosisAsOf` 是模拟业务时间，不等于 HTTP 请求时间 `requestedAt`。
- S1 QUERY 仅 `ASSET_PROFILE` / `MAINTENANCE_HISTORY`；诊断仍进已有 `TaskOrchestrator` 和 `CapabilityGateway`。
- POST 诊断固定 `202 + QUEUED + Location`；真实结果/事件通过 GET 读取。
- S1 不做实时 SSE、可恢复补证、标准 SKILL.md、工业双域、Vue、数据库持久化、完整 Hypothesis 调查闭环。

## 6. 如果一天内做不完

允许以 M0、M1、M2 任一**已通过里程碑**为停止点；在 `state.md` 记录未完成内容和测试事实。M3 内部可停在“运行状态机已验证”的检查点，但未完成最终 Review 时仍保持 `IN_PROGRESS`。**不要为了赶进度把未运行的在线 LLM 验证标为 PASS。**
