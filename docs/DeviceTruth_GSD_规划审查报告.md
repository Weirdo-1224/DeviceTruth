# DeviceTruth V1.0 GSD Core 规划审查报告

**审查日期：**2026-11-09  
**材料：**用户上传的 `.planning.zip`，共 44 个 ZIP 条目（含目录）、13 份 `*-PLAN.md`、63 条需求、37 个任务。  
**结论：有条件通过。建议保留五阶段路线与现有 13 份 PLAN，先做小范围规划修订，再批准 M0。**

> 审查边界：本报告直接检查了上传的规划文档、需求追踪、代码证据说明和计划细节，但 ZIP **未包含** V1.0 原始 PostgreSQL 设计全文和 Java 仓库源码。因此，无法独立验证每个源码引用、设计全量覆盖或重跑 `145/0/0/0` 测试。测试结果属于规划包记录的历史实测，非本次审查复测。

## 1. 已确认的优点

1. **需求来源优先级清晰。** `PROJECT.md`、`INGEST-CONFLICTS.md` 将新版 PostgreSQL 方案置于旧 V0.1/V0.2 文档之上，没有让旧版 FROZEN 限制覆盖新产品方向。
2. **对现有代码做了实质性差距对照。** `GAP-ANALYSIS.md` 的 E01–E22 索引覆盖 HTTP 路由、四字段请求、受控循环、Gateway、Evidence、Guard、内存运行状态、报告与前端，而不只是重新设计一个理想系统。
3. **需求追踪结构自洽。** 经本次独立脚本读取，`REQUIREMENTS.md` 恰有 63 条：已实现 4、部分实现 28、未实现 25、冲突 6；13 个 PLAN 的元数据包含相应需求、任务与依赖。规划包本身也声明并记录了唯一主计划覆盖与 DAG 检查通过；但**结构覆盖不等于语义覆盖**。
4. **架构方向合理。** 单 Agent 主循环、只读设备工具、PG/pgvector、领域 Skill 与知识 RAG 分离、结构化资产时间证据、风险分级保护、早期 Vue、后期 SSE，没有强迫先完整实现旧 Hypothesis 状态机。
5. **执行边界真实。** `STATE.md` 为 `planning / review_pending / execution_authorized=false`，没有将 13 个 PLAN 当成已完成工作或将旧在线结果冒充新版验收。

## 2. 必须先修订的事项（P0）

### P0-1：把最小多轮补证续跑纳入 M1

**现状证据：**`phases/02-open-rag/02-02-PLAN.md` 的 T2 只保证 `ASK_USER -> WAITING_FOR_USER` 落库，明确将恢复留到 `03-02`；`phases/03-durable-investigation/03-02-PLAN.md` 的 T1 才实现把用户回复绑定到旧 run 并续跑。

**问题：**M1 虽然能给出追问，却不能形成最具代表性的「用户补充事实 → Agent 沿同一调查继续 → 引用回答」产品闭环。对话体验容易仍表现为一次性问答。

**最小修改：**
- 在 `02-02` 增加最小 `pendingQuestionId` / `runId` 关联、WAITING → RUNNING（或 QUEUED → RUNNING）转换与上下文恢复；实现原始消息、必要引用与待答问题的持久读取。至少验证同一 run 两轮互动。
- `03-02` 仍负责**跨进程检查点重建、崩溃恢复、租约、CAS 竞态、旧证据重新核验**，不用提前实现完整可靠性工程。
- `REQUIREMENTS.md` 将 `AGENT-03` 的主交付迁至 M1 对应计划，M2 作为强化验证；`E2E-07` 拆为 M1 的基本多轮与 M2 的跨重启续跑，避免 M1 误报完整 E2E PASS。
- `ROADMAP.md` 的 M1 success criteria 明确“回答补充问题后同一 run 继续并产出结果”。

### P0-2：补齐工具和 Skill 真正接入 Runtime 的修改点

**现状证据：**
- `02-01-T2` 要把 `search_knowledge` / `get_document_excerpt` 注册为工具，但 `02-01-PLAN.md` 的 `files_modified` 只有 `CapabilityTypes.java`、KnowledgeService/Controller 等，并未明确 `CapabilityGateway.java` 或 `ServerConfiguration.java` 等实际注册/依赖装配入口。`02-02` 虽包含 Gateway/ServerConfiguration，但其 T1 才要贯通 Agent 主循环。
- `04-01-T2` 写了“把工具绑定与不可信内容边界接入唯一 Runtime”，然而 `04-01-PLAN.md` 只列 Skill 文档、Registry、ContextLoader、SQL 和 Registry 测试，没有列 Agent 服务/Runtime/装配/网关的集成修改位置。
- `04-02-PLAN.md` 的 `key_links` 明确写 `GeneralAgentService.java -> SkillContextLoader.java`，但 `GeneralAgentService.java` 不在该 PLAN 的 `files_modified`。

**问题：**规划宣称的“接入”与要改的文件之间存在缺口，执行时 Codex 可能临时扩大修改范围，或只实现孤立 Registry/SearchService，未打通真实模型调用链。

**最小修改：**逐项确认实际工具注册点、Agent 上下文注入点、Skill 发现与激活点、Spring Bean 装配点和端到端测试位置；将必要文件加入正确 PLAN 的 `files_modified` / `<files>` / `key_links`，允许按 01-01 的 Runtime ADR 确定最终类名，但必须写出明确的集成行为与测试。`02-01` 可以先实现可测试的服务端工具接口，`02-02` 才接入实际 Agent；此时应修正文案，不得在 `02-01` 声称已完成全链路工具注册。

## 4. 执行质量优化（P2）

- 多数 PLAN 的每一个 task 重复粘贴同一长串 `<files>`，`<read_first>` 也只指向笼统“现存源码”。建议针对真实任务缩小文件清单，列出关键类/方法、接口与测试入口，降低 AI 开发时的误改概率。
- `must_haves.artifacts` 中 `pom.xml` 被作为 `01-02`、`02-01`、`02-03` 的“首项真实产物”，信息密度很低；应改成该计划最能代表验收行为的**新契约/迁移/核心服务/测试**组合。
- 不强求每项任务都设置独立审批，也不必为追踪而增加大量流程文件；目标是精确执行计划，而非扩大 GSD 元数据体积。

| **M4** | SSE、报告、正式 E2E、备份恢复和部署 | 保持；扩大此前阶段已开始的验证，而不是首次才测产品质量 |

## 6. 修订完成的验收条件

1. 更新 `PROJECT.md`、`REQUIREMENTS.md`、`ROADMAP.md`、受影响 PLAN，以及 `STATE.md` / `NEXT_SESSION.md`；统一相同需求的主交付、依赖和阶段验收口径。
2. `02-02`（或紧邻的 M1 PLAN）能明确描述并验证**同一 run 的两轮对话**；`03-02` 仍独立覆盖重启恢复与竞争条件。
3. `02-01`/`04-01`/`04-02` 的真正集成点在文件清单和行为测试里可以逐一定位，没有“只实现类但未装配进链路”的空白。
4. 旧 CLI + 原有 145 项基线继续保留；新 PG、模型、embedding、UI、恢复分别报告真实验证/未验证，不混用 fake 与在线结果。
5. 规划修订期间**不修改 Java/依赖/前端/数据库，不执行 PLAN，不改变 review_pending**；仅做规划修改并重新跑 GSD 结构/一致性检查。

## 7. 结论

**不建议推倒重写。** 当前 63 需求与 13 PLAN 的框架值得保留。真正需要修正的是：**M1 的对话闭环、组件接入可执行性、早期实际效果验证，以及少量任务粒度与机器依赖。** 修订完成后，可优先批准 `01-01`，不要一次性自动执行全部 13 个 PLAN。
