## 2. 缺陷清单（仅报可复现或有明确证据的问题）

### M3-P1-01｜白名单事件视图对 7/11 类事件生成事实性错误的 summary/referenceIds（违反冻结 §4.7）— 复审已验证关闭

- 位置：`src/main/java/io/devicetruth/application/RunEventViews.java:37-85`（`view()` + `nestedRaw()` :109-116）；根因配合点 `src/main/java/io/devicetruth/core/runtime/TaskOrchestrator.java:62,64,88,96,119,153`（`Map.of("attempt", attempt)` / `("proposal", action)` / `("result", observation)` / `("verdict", verdict)` 等把 **Java record 原样**放进内存 `RunEvent.data`）。
- 问题：`RunEventViews` 按 `Map<String,Object>` 逐层导航 `event.data()`，但内存中的 data 值是 record（`Attempt`/`ActionProposal`/`CapabilityResult`/`Verdict` 等），`instanceof Map` 判定失败 → 全部取 null。`events.jsonl` 落盘时经 Jackson 序列化所以文件里形状正常，API 走的却是内存 report，因此：
  - `ACTION_PROPOSED` → summary 恒为 `提议动作 UNKNOWN`，referenceIds 恒为 `[]`（应为 `CALL_CAPABILITY` 等真实类型 + capabilityId/candidateRuleId）；
  - `CAPABILITY_RESULT` → 恒为 `能力结果：TOOL_FAILURE`，referenceIds `[]`（**成功的能力调用被显示为失败**，与事实相反）；
  - `GUARD_RESULT` → `结案校验：`（缺 `RULE_AND_EVIDENCE_VERIFIED` 等真实判定码），规则 ID 引用丢失；
  - `HYPOTHESIS_INVALIDATED`/`RULE_SELECTION_INVALIDATED`/`GUARD_REVIEW` → referenceIds 全空；
  - `MODEL_ATTEMPT` → `模型尝试 #null：null`（scripted B 不产生 attempt 事件所以未暴露，在线路径必现）。
- 触发条件：任意一次完成的诊断 `GET /api/diagnoses/{id}/events`（scripted CAR-B 即可复现）。
- 复现证据（Reviewer 独立探针 `EventsProbe`，真实 scripted Core 跑 CAR-B 后打印 `RunEventViews.of(snapshot)`）：34 条事件中全部 7 条 `ACTION_PROPOSED` 为 `提议动作 UNKNOWN`、全部 6 条 `CAPABILITY_RESULT` 为 `能力结果：TOOL_FAILURE`、`GUARD_RESULT` 为 `结案校验：`（空）。现有测试未捕获：`DiagnosisHttpTest` 只断言事件类型名/序号与 TERMINATED 摘要（TERMINATED/STATE_COMMITTED/REASON_INPUT 恰好不依赖 data 导航所以通过）。
- 风险：TC-06「结束后真实事件」的核心——事件来源准确、固定文案可审计——不成立；用户会看到与事实相反的能力结果和 UNKNOWN 动作，事件轨迹不可信。属契约正确性缺陷，非泄漏类（方向是丢数据/错数据）。
- 最小修复建议：`RunEventViews` 导航前把 `event.data()` 规范化为 JSON Map（如 `Json.MAPPER.convertValue(data, Map.class)`，record 序列化形状即视图期望形状，`RunReportWriter` 已证明该形状可落盘），或按 record 组件取值；随后为 scripted B 的 8 类事件补 summary/referenceIds 断言（成功 `能力结果：成功`、`提议动作 CALL_CAPABILITY` + capabilityId、`结案校验：RULE_AND_EVIDENCE_VERIFIED` 等），使该类缺陷不可回归。

## 5. 中文调用链解释（供项目负责人理解新增代码）

1. 入口不变：客户端 `POST /api/sessions/{id}/messages` 说「CAR-B 通信超时」→ `ConversationController.message` → `ConversationFlowService.handle` 路由复核为 DIAGNOSE。
2. `diagnose()`（`ConversationFlowService.java:79-99`）先经 `DiagnosisApplicationService.map` 做 Catalog 固定 `asOf` + 规则存在性校验生成 `DiagnosisGoal`，然后在会话锁内 `commitPlanned`：容量预检 → `DiagnosisRunService.submit` → 一次性写 USER/SYSTEM 两条消息（任何一步失败不留半条）。
3. `DiagnosisRunService.submit`（`DiagnosisRunService.java:165-182`）：生成公开 `diagnosisId`、登记 QUEUED 快照、交给有界线程池（默认并发 2 + 队列 10，`SynchronousQueue` 表达零队列）；执行器拒绝时**同步移除注册项**再抛 429。Controller 固定返回 `202 + Location + QUEUED`，真实状态只能 GET。
4. 工作线程 `execute()`：每任务 `ReasonerFactory.create()` 新建独立 Reasoner（scripted/openai/qwen，未知配置在运行时映射 `MODEL_CONFIGURATION_UNREADABLE`→FAILED，不拖垮容器启动）→ 原样 `new TaskOrchestrator(gateway, new EvidenceManager(), new DecisionGuard()).run(request, budget, reasoner)` → `RunReportWriter` 落盘（报告目录 UUID 仅内部保存）。
5. 收尾 `markCompleted`：`coreTaskId` 只取 `report.state().taskId()`；读 `report.result().runStatus()`，Core 判 FAILED 才置 FAILED（`errorCode` 经 28 项白名单过滤），否则 COMPLETED；快照保存内存事件列表。
6. 查询侧：`GET /api/diagnoses/{id}` 经 `runs.require` 做归属校验（不存在/不匹配同码 404），未结束时结论字段一律 null；结束后 `ConversationController.diagnosisView` 用 `SafePublicFields`（§4.8 白名单）过滤 `stopReason/diagnosisSummary/warnings/openNeeds`。**P1-01 正在 `GET .../events` 的 `RunEventViews`**：它应对同一批内存事件按 §4.7 白名单拼固定文案，但因把 record 当 Map 导航，多数事件的文案/引用生成错误。
7. 会话消息与诊断运行完全解耦：消息只记录「已接受」，结论只出现在诊断端点，完成前事件一律不可读。
