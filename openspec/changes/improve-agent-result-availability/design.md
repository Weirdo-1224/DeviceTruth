# Design

## Context

当前主循环每轮只接受一个动作，工具执行后立即再次请求模型。工具摘要、引用和 Skill 状态已有持久检查点，但没有调查阶段、无进展计数或最终回答预算。模型连接只接受固定 45 秒超时，Run 只能在调用前后协作式检查总时限。答案审核失败后也只有重答或技术失败两种结果。

本设计复用现有 `AgentResult`、`HUMAN_REVIEW`、事件白名单和 PG 检查点，不引入新的前端响应结构或数据库迁移。

## Goals / Non-Goals

**Goals:**

- 用一次模型动作完成最多 3 个独立只读查询，并保持逐工具授权、参数校验、引用登记与审计。
- 用宿主状态机保证调查最终进入回答阶段，而不是依赖模型主动停止。
- 用同一个 Run 剩余时间约束首次模型请求和协议重试。
- 在调查已开展时提供不依赖迟到模型内容的有限结果。
- 保留现有调用方和测试使用的单动作及构造接口兼容形式。

**Non-Goals:**

- 本版不并行执行工具，不引入跨工具复杂 DAG 规划。
- 不放宽证据、设备、确诊、安全和数据性质门禁。
- 不为有限结果自动编造候选故障原因。
- 不修改前端页面，不做浏览器模拟点击或移动端验收。

## Decisions

### 1. 新增 `CALL_TOOLS`，宿主顺序执行小批次

`ActionProposal` 增加批量动作及不含 `type` 的单项查询结构，数量限制为 1 至 3。协议仍只允许一个 JSON 对象。宿主先检查工具名称、当前授权及明显依赖，再复用现有 `CapabilityGateway` 逐项执行。

本版选择顺序执行而非并行：主要收益来自减少模型往返，顺序执行还能保留现有事务、Skill 状态与事件顺序。每个工具完成后保存检查点；恢复时保留已提交前缀，未执行部分由后续模型依据实际结果重新决定。

`activate_skill` 与 `read_skill_reference` 等具有顺序依赖或 Run 状态变化的工具不放入批量动作，仍走单工具路径。

### 2. 主循环增加显式阶段与无进展计数

运行状态在内存和检查点中增加 `finalizing`、`noProgress`，以缺省值兼容旧检查点。每轮根据以下信息计算是否有进展：

- 新增引用数量；
- 工具可见结果指纹；
- 是否出现有效追问或答案。

连续两个调查动作没有新增引用且结果重复或为空时进入最终回答。只剩最后一步或剩余时间不超过 `min(30 秒, 总预算的 1/4)` 时也进入最终回答。小预算测试使用比例上限，避免预留量反而大于整个 Run。

最终回答阶段的工具目录为空，协议反馈明确要求 `ANSWER`。模型仍请求工具、继续输出非法协议或答案再次被拒时，不再回到调查循环，而进入有限结果构造。

### 3. 剩余时间通过运行时传给模型连接

在 `GeneralReasoner` 增加带剩余时间供应器的默认提议方法，旧实现仍走原接口。`GeneralAgentService` 提供“已持久累计时间＋当前执行段耗时”的剩余毫秒数。

`AgentScopeStep` 支持单次请求超时参数，实际取固定 45 秒和剩余预算的较小值。`StructuredAgentReasoner` 的第二次协议重试使用同一供应器重新计算剩余时间，不重置窗口。

供应商传输不能物理中断时，以取消等待、迟到结果不采纳和宿主有限结果为边界，不宣称所有 HTTP 实现都能立即断开连接。

### 4. 有限结果由宿主构造并再次经过 `AnswerGuard`

`AgentRunOutcome` 增加显式 `limited` 标记，避免通过文案猜测结果性质。只有已存在工具执行记录时，最终阶段的模型、协议、预算或答案审核失败才允许降级；首次模型即失败仍保留真实技术失败。

有限结果使用以下保守内容：

- 类别固定为 `HUMAN_REVIEW`；
- 摘要只说明“未能形成可靠诊断，需要人工核验”；
- 不生成故障原因或观测断言；
- 仅引用本 Run 已取得的真实引用，原始摘录作为来源展示，不改写成新事实；
- 在 `uncertainties/limitations` 中记录原原因码和限制；
- 设备对象只使用现有服务端候选集合；
- 最终草稿仍调用 `AnswerGuard`，风险与 `dataNature` 由服务器计算。

发生总超时时，迟到模型提案仍被丢弃，但宿主新构造的有限结果可以完成交付。持久化层仅在 `limited=true` 时允许这种收口，其余超时答案继续按 `TOTAL_TIMEOUT` 拒绝。

### 5. 格式归一化只处理明确变体

在 Jackson 严格解析前，通过 JSON 树去除代码围栏并规范已知动作及枚举字段大小写。无法可靠识别的字段、错误类型、未知动作、引用和安全语义不做猜测，仍走原失败与有限结果路径。

`kind/relevance` 只用于结果展示，不再作为整份答案的拒绝依据：`DIRECT + kind=UNKNOWN` 降为 `relevance=UNKNOWN`，`UNRELATED` 候选保留为背景信息。该放宽不改变引用、设备对象、危险操作和未核验确诊门禁。

### 6. 事件保持白名单兼容

复用现有 `RUN_MODEL`、`RUN_TOOL`、`ANSWER` 和 `RUN_FAILED`，按需增加白名单事件 `RUN_PHASE`、`RUN_DEGRADED`。载荷只包含阶段、动作数量、原因码和新增引用计数，不包含参数原文、Prompt 或模型原文。

## Risks / Trade-offs

- [批量中的部分工具失败可能导致信息不完整] → 每项独立记录结果与检查点，失败原因进入反馈，不把失败当成证据。
- [无进展判定可能过早停止] → 需要连续两轮且同时满足无新增引用与结果重复/为空，最终回答仍可说明资料缺口。
- [有限结果被误解为正常诊断] → 固定 `HUMAN_REVIEW`、高风险处置和原失败原因限制，不输出候选原因。
- [旧检查点缺少新增字段] → 使用缺省 `false/0` 和兼容构造器，不改变现有数据库结构。
- [真实模型行为不一定主动使用批量动作] → 协议明确优先批量独立查询；即使模型仍单步调用，无进展和最终阶段也能保证收口。

## Migration Plan

1. 先部署兼容旧单工具动作和旧检查点的后端，无需数据库迁移或前端同步发布。
2. 执行核心协议、运行时、AnswerGuard 和真实 PG 生命周期测试，再执行全量 Maven 测试、前端测试及构建。
3. 重建 product 后端供用户手动端到端操作，保留原失败 Run 供对照，不修改历史结果。
4. 若出现协议兼容问题，可回滚后端版本；旧 `CALL_TOOL` 和既有结果事件未做破坏性修改。
