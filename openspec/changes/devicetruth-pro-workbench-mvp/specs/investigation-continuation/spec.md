# Spec Delta

## Purpose

让用户以已有判断和来源为起点继续调查，同时保留每一轮的结果及证据边界。明确普通补充开新一轮、等待问题的补答恢复原一轮，复用既有消息协议和授权规则完成专业检修的人机协作。

## ADDED Requirements

### Requirement: 深入调查创建后续轮次

用户显式点击深入调查时，系统 SHALL 在当前会话提交包含选中判断原文的可见请求，不携带 replyTo，并返回可追踪的新 Run。已有历史保留；新结果按新 Run 展示，不覆盖或语义合并旧结果。没有选中判断、提交中或当前调查尚未结束时 SHALL 禁用深入调查。

#### Scenario: 从候选原因继续调查

- **WHEN** 当前轮已完成，用户选中候选原因并点击深入调查
- **THEN** 同一会话增加一个 Run，界面显示该轮进度，完成后展示新结果且仍能查看上一轮

#### Scenario: 从一般判断或普通文字继续调查

- **WHEN** 已完成结果不是候选原因类别，用户选择现有一般判断深入调查，或在没有可选判断时提交普通文字继续调查
- **THEN** 沿用实际结果语义创建后续 Run；普通文字入口不要求先选择判断，也不伪造候选原因或引用

#### Scenario: 连续点击和提交响应丢失

- **WHEN** 用户连续点击深入调查，或同一次提交因响应丢失而重试
- **THEN** 按钮防重且同一逻辑提交复用幂等键，不产生两个调查轮次；尚未确认提交结果时先查询历史，不自动生成新键重发

### Requirement: 继承引用遵守真实授权范围

深入调查 SHALL 仅从所选判断关联的已取得引用构造 contextRefs，每项仅含 referenceId，去重且最多 10 项。服务端沿用 owner/project 授权，拒绝不存在或越权引用。新轮答案 SHALL 使用新轮重新登记的引用 ID，不假定旧 ID 可直接引用。

#### Scenario: 合法证据继承

- **WHEN** 用户深入调查的判断关联三条已取得且服务端授权的引用
- **THEN** 提交这些引用的 ID，由服务端登记到新 Run，前端从新 Run 读取实际引用及答案关联

#### Scenario: 引用不存在或越权

- **WHEN** 提交引用不再存在或属于其他 owner/project
- **THEN** 展示拒绝结果，不伪装为成功调查，不绕过授权或自行补造引用

#### Scenario: 关联引用超出上限

- **WHEN** 所选判断关联超过 10 条可用引用
- **THEN** 提交前明确显示按原顺序继承的前 10 条及省略数量，实际请求不超过上限

### Requirement: 现场补充与待答问题分流

工作台 SHALL 将已结束轮次的普通现场补充作为用户报告提交为新消息、新 Run；WAITING_FOR_USER 状态 SHALL 使用当前问题的 runId、pendingQuestionId、questionVersion 三元组补答，恢复同一 Run。QUEUED/RUNNING 时保留输入草稿并禁止另开并发调查。

#### Scenario: 结束后的现场补充

- **WHEN** 当前轮已结束且用户提交现场观察
- **THEN** 无 replyTo 的消息创建新 Run，原始陈述保留为用户报告，旧结果仍可回看

#### Scenario: 回复当前追问

- **WHEN** 当前轮等待用户，用户填写补答并提交
- **THEN** 携带完整当前三元组，原 Run 恢复执行，会话 Run 数量不因此增加

#### Scenario: 问题版本已过期

- **WHEN** 补答被服务器以等待状态或问题版本冲突拒绝
- **THEN** 保留草稿、重新读取 Run 并提示当前问题，不静默转换成普通新消息
