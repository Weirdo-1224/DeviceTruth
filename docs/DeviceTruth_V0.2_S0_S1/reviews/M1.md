### 2.1 在线模型资产猜测与覆盖（M1-P1-01）

冻结依据：task §3.2 必做 2/5，spec §5.1“缺资产（如这台设备且无上下文）→CLARIFY”，修订方案 TC-07。

本轮真实启动 online Server，连接**本机 HTTP 模型替身**，替身仅返回合法模型建议 JSON。没有外部模型调用，也没有直接伪造 Controller 返回。

1. 新建 session，提交 `{"content":"这台设备通信超时"}`，没有 hint/上下文。替身返回 `{"route":"DIAGNOSE","assetId":"CAR-B","queryKind":null,"symptomText":null,"reason":"review-local"}`。实际 **501 NOT_IMPLEMENTED**；应为 **200 CLARIFY**。
2. 另建 session，先提交 `CAR-B 帮我看看`，替身建议 `CLARIFY/CAR-B`，实际 200、assetId=CAR-B。
3. 同 session 提交 `这台设备帮我看看`，替身建议 `CLARIFY/CAR-C`，实际 **200、assetId=CAR-C**，用户未选择 C。

调用链：LlmTaskRouter.decide → validateSuggestion → resolveAsset 在没有文本资产时优先接受模型候选 → FlowService 在 CLARIFY 分支前更新 currentAssetId。风险是本轮错误绑定/分类，并为后续查询诊断提供错误资产；**本轮未宣称已经跨资产执行 Core**。

### 2.2 显式未知编号与多资产歧义（M1-P1-02）

冻结依据：task §3.1.5、§3.2.2/5，spec §4.1 的唯一资产白名单/未登记资产不复用 CAR-B。

本轮 offline Server 中先用 `CAR-B 帮我看看` 建立上下文，然后分别发送：

- `CAR-Z 通信超时` → 实际 **501 NOT_IMPLEMENTED**；应 UNSUPPORTED（或先澄清，不能自动选 B）。正则仅识别 `[A-Z]{2,}-[0-9]{2,}`，CAR-Z 不命中；Catalog 不命中后直接使用 currentAssetId=B。
- `CAR-B 和 CAR-C 通信超时` → 实际 **501 NOT_IMPLEMENTED**；应澄清目标。catalogAssetInText 在 Catalog 遍历遇到 B 就 return，未检测到多个候选。

两次 501 均结合明确源码分支证明进入了诊断类别；HTTP 错误体本身不包含资产，本报告不假称从错误体读出了 B。

### 2.3 危险请求在线复核缺失（M1-P1-03）

冻结依据：task §3.2.5、spec §5.1 及“任何 route 都要程序复核”、修订方案 TC-09。

本轮 online HTTP 输入 `帮我重启 CAR-B 通信超时`，替身合法建议 DIAGNOSE/CAR-B，实际 **501 NOT_IMPLEMENTED**；应 **200 UNSUPPORTED**。同类离线危险词测试能通过，无法覆盖在线路径。

当前 Gateway 仍只读，未观察到设备控制被执行，因此不定 P0；问题在于当前 M1 必需的边界拒绝依赖模型自觉，程序未兑现冻结契约。

### 2.4 会话容量拒绝残留写入（M1-P1-04）

冻结依据：task §3.2.2 的线程安全有界会话及明确上下文，spec §8/§6.1 容量拒绝。

本轮真实 offline HTTP 使用 `maxMessagesPerSession=3`：

1. `CAR-B 帮我看看` → 200，GET 为 USER(B)+SYSTEM 两条。
2. `CAR-C 帮我看看` → **429 SESSION_CAPACITY_EXCEEDED**。
3. 随后 GET 仍为 200，但消息变成 **3 条**，最后一条是被拒绝请求的 USER `CAR-C 帮我看看`，没有对应 SYSTEM。

源码另直接证明：即使配置为 2、原消息已满，第二轮也会先在 FlowService:34 把 currentAssetId 改成 C，再在 :36 被拒绝。该“已满时改上下文”分支本轮没有通过私有字段反射另测，证据是完整调用顺序；奇数容量半写入已由 HTTP 复现。

风险是客户端收到拒绝但服务端接受了部分交互，GET 记录与回复不一致，后续“这台设备”可能使用被拒绝请求的资产。并发时单次 append 的锁也不能让两条消息及资产绑定共同提交。
