# Spec Delta

## Purpose

确保每次调查都有明确、可恢复且在各视图中一致的本轮排查对象，避免补答变更、多资产读取或历史数据造成设备上下文矛盾。

## ADDED Requirements

### Requirement: 本轮排查对象持久化
系统 SHALL 为每个 Run 保存排查设备、确认状态和变更来源，并在刷新、重连及崩溃恢复后返回相同上下文。初始状态 MUST 区分已选择与未确认。

#### Scenario: 初始提交已选择设备
- **WHEN** 用户选择设备并发起新 Run
- **THEN** Run 返回该设备及已选择状态，后续回读仍保持一致

#### Scenario: 初始提交未选择设备
- **WHEN** 用户不指定设备发起新 Run
- **THEN** Run 返回未确认状态而不是虚构设备或已确认状态

#### Scenario: 结构化补答变更设备
- **WHEN** 用户在原 Run 的补答中明确选择另一台设备
- **THEN** 系统在同一持久事务中更新排查对象并记录变更来源，后续执行和回读使用新对象

### Requirement: 排查对象确认与歧义保护
系统 MUST 仅在最终答案声明、用户显式选择和合法资产工具访问相互一致时确认对象。系统 MUST NOT 根据最后一条消息或最后一次工具调用自动选定设备。

#### Scenario: 自由文本补答后确认设备
- **WHEN** 用户通过文字明确更换设备且最终答案声明的对象与该上下文及实际授权资产访问一致
- **THEN** Run 将新对象标记为已确认并保留原对象的变更信息

#### Scenario: 最终答案对象冲突
- **WHEN** 最终答案声明的设备不属于该 Run 的合法候选或与用户明确选择冲突
- **THEN** 系统拒绝将该答案作为有效结论并进入既有答案重试或失败链路

#### Scenario: 多资产无法唯一确定
- **WHEN** 一个 Run 合法涉及多台设备且没有可确认的主排查对象
- **THEN** Run 返回歧义状态及实际可用上下文，不自动选择其中一台

### Requirement: 产品视图使用统一排查对象
任务卡、设备快照、深入调查、会话摘要和报告 SHALL 使用同一个 Run 排查对象及确认状态。未确认或歧义状态 MUST NOT 被展示为已关联或已确认。

#### Scenario: 补答后查看完成结果
- **WHEN** 用户在补答变更设备后查看已完成 Run
- **THEN** 任务卡、设备快照、深入调查和报告均显示新对象，并可说明原对象已发生变更

#### Scenario: 查看对象未确认的结果
- **WHEN** Run 的排查对象为未确认或歧义
- **THEN** 产品显示待确认原因且不自动呈现某台设备的确认快照

### Requirement: 历史 Run 兼容
系统 SHALL 在缺少新排查对象字段时提供保守回退，不得根据历史工具记录推断已确认对象。

#### Scenario: 旧 Run 有初始选择
- **WHEN** 读取只有目标消息设备而没有新确认字段的历史 Run
- **THEN** 系统按已选择状态展示该设备，不将其升级为补答后已确认

#### Scenario: 旧 Run 无初始选择
- **WHEN** 读取没有目标消息设备和新确认字段的历史 Run
- **THEN** 系统显示未确认且其余消息、答案和引用仍可使用
