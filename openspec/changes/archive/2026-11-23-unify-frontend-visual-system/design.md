# Design

## Context

前端入口由 `main.ts` 引入 `design.css` 和 `workspace.css`，`App.vue` 再引入 `pro.css`；各页面另有 scoped 样式，管理端通过独立入口加载压缩的 `admin.css`。当前已有 `--primary`、`--text-*`、`--line`、语义色和圆角令牌，但 `.team-app`、`.pro-light` 及组件样式多次覆盖，同类控件和反馈样式分散。

本次以 `proposal.md` 和 `specs/frontend-visual-system/spec.md` 为行为边界。现有 Vitest 主要覆盖数据合同和视图逻辑，没有视觉截图基线；因此浏览器验收必须成为交付的一部分。产品浏览器联调默认连接启用真实大模型的 product 后端，不能用健康检查或 scripted 服务代替真实主流程验收。

## Goals / Non-Goals

**Goals:**

- 建立一个来源明确、覆盖关系可预测的共享视觉层。
- 尽量保留现有模板和类名，通过共享样式与局部属性补齐统一外观和状态。
- 使用户端与管理端共享文字、语义色、控件和反馈规则，同时允许管理端保留深色导航作为入口识别。
- 让视觉验收覆盖真实交互和关键边界状态，而非只检查构建结果。

**Non-Goals:**

- 不引入组件库、CSS 框架、设计令牌构建工具或截图测试框架。
- 不重排页面功能、不改路由、不抽象一套大型 Vue 基础组件体系。
- 不删除与本变更无关的旧样式文件，不格式化无关代码，不修改后端或数据合同。
- 不新增比现有业务规则更严格的前端校验，也不根据错误文案猜测字段归属。

## Decisions

### 1. 以 `design.css` 作为共享令牌唯一基线

在现有 `:root` 中补齐字号、字重、间距、控件高度和状态色令牌；品牌色、文字色、边框、语义色、圆角和阴影继续沿用当前蓝色体系。`.team-app` 与 `.pro-light` 只保留确有场景差异的布局变量，不再重复定义同义颜色。管理端将自有品牌变量映射到共享令牌，字体、焦点和语义状态直接引用共享值。

备选方案是新建独立主题文件或引入 tokens 构建工具；当前只有一个产品主题，新增构建层没有必要。

### 2. 保留现有 CSS 分层，收敛职责而不做大规模组件重写

- `design.css`：重置、令牌、焦点和跨入口基础规则。
- `workspace.css`：共享 `dt-` 控件、卡片、列表、表格、反馈和空状态样式。
- `pro.css`：专业工作台独有布局与运行状态，不再承担通用提示和按钮的重复定义。
- 组件 scoped 样式：只保留组件独有布局、截断和特殊内容表达。
- `admin/admin.css`：保留管理端布局与深色导航，复用共享语义和控件规格。

优先给现有 `dt-button`、`dt-field`、`dt-tag`、`dt-empty`、`error` 等类补齐共享规则，避免为了减少 CSS 而重写所有 Vue 组件。只有无法通过选择器职责解决时才调整模板 class。

### 3. 使用有限、可检查的文字与尺寸层级

正文以 16px 为基准，辅助信息和元数据以 14px 为下限，标题按页面、章节、子章节分层。主要按钮和表单控件统一高度、内边距、边框及圆角；紧凑表格可调整垂直密度，但不缩小业务文字到 14px 以下。

同类页面容器使用统一的内容宽度和间距来源。新建与已有调查保留各自表单/结果布局差异，但共享主内容对齐和最大宽度，避免提交后的无意义跳变。

### 4. 用语义修饰类统一反馈，而不是新增通用反馈组件

加载、处理中、成功、错误和空状态继续使用现有原生 HTML 与 `role="status"` / `role="alert"`，通过共享语义类统一背景、边框、图标间距和文字颜色。可恢复错误保留现有重试事件，只统一按钮位置与外观；空状态保留各页面业务文案和下一步，不强制填入无意义插图。

选择共享 CSS 而不是新 `Feedback.vue`，是因为各页面的条件渲染、重试参数和空态操作不同，新增组件会扩大模板与事件合同修改面。

### 5. 复用现有状态数据表达 Run 与控件状态

运行状态继续使用已有 `run.status`、状态文案和图标，不新增前端状态映射。结果卡和报告补充与现有状态对应的 class 或数据属性选择器，使 FAILED、CANCELLED、WAITING_FOR_USER 等状态有一致且可区分的外观。

按钮与页签继续使用现有 `aria-pressed`、`aria-selected`、`aria-current`、`disabled` 和 `active` 作为样式钩子，不为视觉统一另建交互状态。所有动画如被保留或新增，必须提供 `prefers-reduced-motion` 降级。

### 6. 字段错误采用渐进增强和明确关联

对现有原生必填、格式及长度校验，使用稳定的字段说明 id、`aria-describedby` 和适用的 `:user-invalid` / `aria-invalid` 样式。只有服务端错误合同已明确指向字段时才做字段级映射；其余错误保持表单级提示，不通过匹配自然语言猜测目标字段。

输入禁用态与按钮禁用态共享颜色令牌，同时保留现有禁用逻辑、草稿保留和权限判断。

### 7. 响应式沿用现有布局策略，集中修复溢出与密度

保留桌面侧栏、窄屏单列和资料区重排的总体策略，以 1440px、768px、375px 作为主要检查宽度。表格继续在自己的容器内横向滚动，不为本次变更重写为卡片列表；修复页面级横向溢出、过小文字和操作区拥挤即可。

### 8. 先建立基线，再分层修改并做真实浏览器回归

实施前记录关键页面和状态的截图及当前测试基线。按“令牌与共享控件 → 用户端页面 → 管理端 → 字段和状态补齐”的顺序修改，每层完成后检查受影响页面。

最终执行 `npm run test -- --run` 与 `npm run build`，并在真实 product 服务上检查登录、新建调查、活动 Run、补答、完成结果、报告、引用及团队页面。难以通过现有真实数据触发的失败或空态可使用明确标注的离线回归手段验证，但不得把它表述为真实模型验收。

## Risks / Trade-offs

- [全局选择器调整影响未逐页检查的组件] → 先记录页面清单与截图，按共享层、用户端、管理端分批回归，避免一次性覆盖所有选择器。
- [提高辅助字号和控件尺寸导致窄屏溢出或信息密度上升] → 在 768px 和 375px 下验证长文本、表格与操作区，优先调整布局和换行，不重新缩小文字。
- [scoped 样式与 `pro.css` 的加载顺序造成局部覆盖] → 明确通用规则与组件规则的职责，检查计算后样式，不通过无节制提高 specificity 或添加 `!important` 解决。
- [管理端共享令牌后失去入口识别] → 保留深色侧栏和必要品牌差异，只统一文字、语义、控件与状态。
- [字段级错误合同不足，无法实现所有服务端错误的精确关联] → 仅映射明确字段错误，其余采用可辨认的表单级反馈，并在验收记录中列明。
- [没有自动截图回归，后续仍可能出现视觉漂移] → 本次保存人工浏览器验收矩阵和结果；不为此额外引入测试框架。

## Migration Plan

1. 记录当前测试、构建和关键页面视觉基线。
2. 先修改共享令牌及基础控件，检查登录页和一个工作区页面。
3. 迁移调查、报告、证据及工作区其他页面，再迁移管理端。
4. 补齐字段关联、运行状态、响应式和减少动态效果规则。
5. 执行完整前端测试、构建和浏览器状态矩阵，记录实际结果与未验证项。

本次不涉及数据库或接口迁移。若出现回归，可按上述层次回退对应 CSS 或模板属性修改；不得通过回退业务逻辑或数据文件解决视觉问题。
