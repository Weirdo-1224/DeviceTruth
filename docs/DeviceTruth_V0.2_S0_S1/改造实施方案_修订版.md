> **文档定位**：基于现有 Java Core 的可执行开发规格，供评审和 Codex 分阶段实施  
> **版本**：v0.2.1-S0S1（修订 Draft，替代 v0.2.0-S0S1）  
> **日期**：2026-11-07  
> **今天的范围与顺序不变**：**S0 基线保护和契约确认 → S1 最小自然语言交互与 HTTP 诊断闭环**  
> **后续阶段顺序不变**：**S2 多轮会话/补证恢复 → S3 标准 Skill/双域场景 → S4 Vue 工作台**

## 0. 修订说明和执行摘要

### 0.1 本次修订保留什么、不改变什么

本次是**技术契约修订**，不是重新制定路线图。继续以“今天让自然语言 HTTP 请求调用现有 Core”为目标：

```text
S0：只读核对真实源码 → 回归 CLI/测试 → 冻结接口与运行方案
S1：HTTP 中文请求 → 轻量 TaskRouter → QUERY 或 DIAGNOSE
    → 受控查询 / 现有 TaskOrchestrator → 查询结果、诊断结果与结束后事件
S2：多轮对话、补证/暂停/恢复；同时补齐 Hypothesis 的专业调查闭环
S3：标准 SKILL.md、工业 SC-0245-B、新能源汽车双域与专业数据
S4：Vue 工作台与运行轨迹可视化
```

**不会**为了 Hypothesis 缺口先插入 S0.5、调换 S1 与 S2，或先修完全部 Runtime 才允许做 HTTP。该缺口确实重要，已被明确登记为 **S2 的必要能力与独立验收项**，不再遗漏。

**今天完成的是“自然语言进入既有证据/规则驱动 Core”，不是“完整开放式 O-H-E-D 故障调查能力已经实现”。** 不得在验收报告或比赛演示中混淆二者。

### 0.2 今天交付的最小用户链路

```text
用户自然语言（HTTP，不做 Vue）
  → ConversationService 保存消息与当前资产上下文
  → TaskRouter 返回 QUERY / DIAGNOSE / CLARIFY / UNSUPPORTED
     ├─ QUERY      → QueryService → 有边界的只读 Repository → 有来源的回答
     ├─ DIAGNOSE   → SupportedScenarioCatalog 校验模拟场景
     │                 → DiagnosisApplicationService → 每任务独立 Reasoner
     │                 → TaskOrchestrator（旧 Core 原样运转）
     │                 → 受控结果 / DiagnosisRunService
     ├─ CLARIFY    → 请求缺失的设备或症状信息
     └─ UNSUPPORTED→ 明确未接入的资产、故障或危险操作

GET /api/diagnoses/{id}          → 任务真实执行状态与最终诊断结果
GET /api/diagnoses/{id}/events   → 任务结束后返回脱敏/白名单事件
```

**S1 不含：** Vue、用户上传新证据后继续同一任务、可恢复等待态、标准 Skill Loader、工业正式场景、真实 IoT 接口、跨进程持久化。若诊断结果是 `NEED_EVIDENCE`，可说明缺少什么，**不能**假装已经支持等待用户回复后恢复原任务。

### 0.3 已证实的 V0.1 事实（需在 S0 重新核对）

- Java 21 / Spring Boot 3.5.x / AgentScope Java 2.0.x；当前主要使用 AgentScope **Model API**，不使用 `ReActAgent` 的内部循环。
- 自研 `TaskOrchestrator + Reasoner + CapabilityGateway + EvidenceManager + DecisionGuard + StateManager`；五类 `ActionProposal`。
- 现有真实 CLI 场景是 `A/B/C/D`，模拟数据域 `automotive-demo`；**E 是未知工具/伪造证据负例测试，不是 CLI 场景**。
- 当前可运行的 B 为 `CAR-B / COMM_TIMEOUT`，**不是**工业 `SC-0245-B`。
- 此前报告 42 项测试通过；DeepSeek/OpenAI-compatible 的 B 场景有两次真实在线验证。以上是历史基线，**不是本文执行后的新测试结果**。
- 当前 `AssetRepository` 只有 `profile(assetId)`、`history(assetId, componentId)` 一类只读查询；没有 `domainOf/listAssets` 等资产元数据 API。
- 当前 `RuleRepository` 只有 `query(domain, symptomCode)`；没有 `listSymptoms` 或领域故障码目录。
- `CapabilityGateway.execute(DiagnosisRequest, CallCapability)` 接受**完整诊断作用域**，不是可直接服务普通事实查询的通用查询接口。
- `StructuredReasoner` 含可变的调用尝试记录；在线 Reasoner 具有延迟初始化字段，**不能作为所有并发任务共享的 Singleton Reasoner**。
- `TaskOrchestrator.run()` 中事件列表为局部变量；**默认只在运行结束后从 RunReport 拿到完整事件**。
- V0.1 提供 `PROPOSE_HYPOTHESIS` 与假设失效逻辑，但现有真实模型轨迹不足以证明完整的 `OPEN → SUPPORTED → INVALIDATED` 假设调查闭环。

原始依据：V0.1 `spec.md/task.md/state.md`、2026-11-06 源码审查与 2026-11-07 Codex 对初版 S0/S1 方案的只读审查。**Codex 在 S0 仍须以当天真实仓库为准核对以上事实。**

## 1. 现状、目标和不可跨越的边界

### 1.1 当前已有模块：保留为默认策略

| 现有模块 | 真正的职责 | S0/S1 处理方式 |
| --- | --- | --- |
| `TaskOrchestrator` | 单步动作循环、预算、终止、事件 | 原样复用；S1 不为实时事件重写循环 |
| `Reasoner` / `StructuredReasoner` | 每轮提出一个结构化动作 | 保留协议；**每次诊断新建 Reasoner** |
| `AgentScopeStep` | 单次模型调用的 SDK 适配 | 保留；TaskRouter 使用独立 Prompt/DTO |
| `CapabilityGateway` | 诊断工具作用域、只读、参数校验 | 只用于原有诊断工具链；普通查询另做受限适配 |
| `Repositories` / `JsonRepositories` | 已有模拟资产、证据、规则源 | 保留；不假设不存在的资产目录接口 |
| `EvidenceManager` | 时间、冲突、事实重建、依赖失效 | S1 不改算法 |
| `DecisionGuard` | 已有模拟规则和证据结案约束 | S1 不放宽既有 `RESOLVED` 条件 |
| `DiagnosisState` / `StateManager` | 每个诊断内部状态 | 每次 Core 执行隔离；原有内存语义不变 |
| `RunReportWriter` | 保存结果和运行轨迹 | 可复用；对外保存 reportPath 与 ID 映射 |
| `DeviceTruthApplication` | CLI 单次运行入口 | **保持 `java -jar ... --scenario=B` 旧命令可用** |

### 1.2 本次新增职责（而不是第二个 Agent）

| 新职责 | 最小模块 | 本阶段是否必需 |
| --- | --- | --- |
| 对话和当前资产绑定 | `ConversationService` | 是；仅轻量单机内存 |
| 用户请求分类 | `TaskRouter` | 是；受限真实/离线两模式 |
| 演示资产/故障/诊断时间目录 | `SupportedScenarioCatalog` | 是；不冒充正式资产主数据 |
| 受限的事实查询 | `QueryService` | 是；固定两类只读查询 |
| 用户目标到 Core 请求的转换 | `DiagnosisApplicationService` | 是；不强制更改 Core DTO |
| 异步诊断任务管理 | `DiagnosisRunService` | 是；每任务 Reasoner、受控容量 |
| Spring Boot HTTP 服务 | Server Main + Controller/DTO | 是；与 CLI 明确分离 |
| Skill、长期记忆、复杂状态恢复 | 后续阶段 | 否 |

### 1.3 四条核心原则

1. **模型提议，程序验证**：Router 只建议路径；LLM 不得直接授予工具权限或批准结案。
2. **来源与时间明确**：所有设备事实均有模拟来源、有效时间和不确定边界。
3. **CLI 回归兼容**：原有 V0.1 行为、报告结构、动作协议与 Guard 不因 S1 变化。
4. **开放输入 ≠ 开放能力**：可用中文表达问题，但目前只能查询/诊断已登记的模拟资产与症状；不把原有规则包包装成完整通用诊断。

### S0-03：冻结双入口与打包方案（解决真实 Main 冲突）

当前 CLI 设置了 `WebApplicationType.NONE`，并在单次任务结束后关闭 Context。**不能单纯加 Web 依赖或删除 NONE 就宣称两个入口自动兼容。**

选定方案：**两个明确的 Main，保留原 CLI JAR 默认入口不变；新 Server 作为独立的启动入口。**

```text
DeviceTruthApplication（原有）
  → WebApplicationType.NONE → --scenario=A|B|C|D → 写报告 → 正常退出

DeviceTruthServerApplication（新增）
  → Web/Servlet 模式 → 持续提供 HTTP → 不调用 System.exit
```

- `DeviceTruthApplication` 保留原有 `java -jar <当前产物> --scenario=B --reasoner=scripted` 行为。
- Spring Boot Maven Plugin **显式固定现有 CLI mainClass**，避免出现两个 Main 后重新打包时随机选主类。
- Server 在 S1 使用单独的 Spring Boot Maven Run 入口（指定 Server 主类），或通过当前依赖支持的显式 classpath 命令启动；**由 Codex 用真实命令跑通并写入 README**。
- S1 不要求再制作第二份 fat JAR；后续若发布 Server JAR 再单独设计 packaging profile。
- Server 应只扫描需要的 Web / Application 配置包，不将 CLI 生命周期代码意外注入 Web；具体 `@ComponentScan` 范围按现有包树核对。
- CLI 执行完能退出；Server 启动后保持服务并提供健康检查。两者有独立启动验证命令。

如果现有 Maven 插件/主类选择不支持该方式，Codex 需列出最小替代方案并记录实际取舍，**不得为了 Web 成功而牺牲旧 CLI 命令**。

### S0-04：冻结时间语义（解决历史证据失效）

必须区分：

| 字段 | 含义 | 来源 |
| --- | --- | --- |
| `requestedAt` | 用户何时提交 HTTP 请求 | 接入时的服务器时间 |
| `diagnosisAsOf` | 诊断重建状态的业务时间点 | 当前模拟场景 Catalog 的固定时间，未来由业务上下文决定 |

已审查的 `CAR-B` 样本：

```text
B 原 CLI asOf               = 2026-11-03T04:00:00Z
CAR-B-FIELD-1 observedAt    = 2026-11-03T03:00:00Z
CAR-B-FIELD-1 validTo       = 2026-11-04T00:00:00Z
```

所以 HTTP 在 2026-11-07 接受请求时，**不可直接用当前时间替换 `diagnosisAsOf`**，否则现场证据可能已过期，结果从 `RESOLVED` 变为 `NEED_EVIDENCE`。这是时间语义差异，不是 Core 错误。

S1 必须从 `SupportedScenarioCatalog` 拿到固定模拟 `diagnosisAsOf`，调用旧 Core 时继续使用该时间。API/结果中明确同时返回：

```json
{
  "dataNature": "SIMULATED",
  "requestedAt": "2026-11-07T10:00:00Z",
  "diagnosisAsOf": "2026-11-03T04:00:00Z"
}
```

**表述必须准确**：本次是“使用现有模拟记录、以历史业务时间点进行诊断”的代码计算，不是对现实设备在请求当天的实时诊断。

### S0-05：冻结演示资产目录契约（不改正式 Repository）

现有 Repository **不具备** `domainOf`、`exists`、`listAssets`、`listSymptoms` 等功能，S1 不假设它们存在。

建议新增 `SupportedScenarioCatalog`，从现有 `datasets/scenarios.json` 及经验证的演示映射加载：

```java
record SupportedDiagnosis(
    String assetId,
    String domain,
    String symptomCode,
    Instant diagnosisAsOf
) {}
```

- 显式记录资产 `CAR-A/B/C/D` 的已支持模拟领域、症状码和对应业务时间；不凭空补一套“真实资产主数据”。
- `TaskRouter` 输出的设备 ID 须经 Catalog 验证；不能把未知设备 `SN-0245` 自动重定向到 `CAR-B`。
- `SymptomResolver` 只对 Catalog 已声明的 `symptomCode` 进行受限别名匹配，并用 `RuleRepository.query(domain, symptomCode)` 验证存在可用规则；**不能依赖不存在的症状枚举 API**。
- 对明确已有 `assetId` 但无法确认故障类别的请求，返回 `CLARIFY` 或 `UNSUPPORTED`，不虚构症状码。
- Catalog 是 **S1 演示适配器**；S3 加入正式领域数据时可用真实设备元数据机制替换。

### S0-06：冻结运行 ID、状态与事件契约

**三个 ID 含义必须明确：**

| 标识 | 谁创建 | 对外用途 |
| --- | --- | --- |
| `diagnosisId` | S1 应用层，接受任务时 | **唯一公开的诊断查询主 ID** |
| `coreTaskId` | V0.1 `StateManager` | 内部对应 Core 的状态/运行记录；完成后可映射 |
| `reportPath` / report run UUID | 现有 `RunReportWriter` | 内部调试路径；不要暴露绝对本地路径 |

`DiagnosisRunSnapshot` 的建议结构：

```text
DiagnosisRunSnapshot {
  diagnosisId: UUID
  sessionId: UUID
  coreTaskId: String?        // 未获得或任务未完成时为空
  reportPath: String?        // 仅服务内部使用
  executionStatus: ExecutionStatus
  outcome: DiagnosisOutcome? // 仅完成且有可用业务结论时存在
  requestedAt: Instant
  diagnosisAsOf: Instant
  dataNature: SIMULATED
  createdAt, startedAt?, completedAt?: Instant
  errorCode?: String
}
```

应用层叫 `ExecutionStatus`（**不要**再定义同名 `RunStatus`）：

```text
QUEUED → RUNNING → COMPLETED
                 └→ FAILED
```

Core 仍用原来的 `RunStatus.ACTIVE/COMPLETED/FAILED`，业务 outcome 仍是 `RESOLVED/NEED_EVIDENCE/CONFLICT/ESCALATE`。**RunService 必须检查返回 `RunReport.result().runStatus()`，不能因为 Future 正常完成就自动标 COMPLETED。**

S1 事件策略明确选 **结束后读取**：

```text
QUEUED/RUNNING → events: []，eventsAvailable: false
COMPLETED/FAILED → 有最终 RunReport 时返回事件白名单视图
FAILED 且无报告 → events: []，eventsAvailable: false
```

不在今天做事件推送或 `RunEventListener`；S4 再决定是否需要实时展示。API 不得使用不存在的 Core 事件类型 `CAPABILITY_CALLED` 冒充真实事件，优先采用实际 `CAPABILITY_RESULT` 等类型。

### S0-07：冻结在线/离线模型、并发与安全策略

**Reasoner 生命周期**：每个 Diagnosis Run 必须通过 `ReasonerFactory.create()` 获得一个独立的实例，不能将 `StructuredReasoner`、`OpenAiReasoner` 或 `QwenReasoner` 作为可并发共享的 Singleton Bean。诊断内部状态和 `attempts` 必须相互独立。

**模型运行模式**：

| 模式 | Router | Core Reasoner | 目的 |
| --- | --- | --- | --- |
| 离线/CI | Stub 或**明确限制范围**的确定性路由 | 每任务新建 `ScriptedReasoner` | 不依赖 API Key，可稳定验证接口和受控流程 |
| 在线验证 | 独立结构化 LLM Router | 每任务新建 `OpenAiReasoner` 或 `QwenReasoner` | 验证真实语言理解和 Core 模型动作 |

- 运行模式由**服务端配置**决定，不允许 HTTP 客户端提交 `baseUrl/model/apiKey`，也不对外开放任意 `reasoner` 切换。
- Router 与 Core 可复用服务器已有安全的模型连接参数，但各自 Prompt/输出 DTO 独立；Router 只分类一次，不产生第二套工具调用循环。
- 在线 Router 不可用：返回明确依赖异常，或仅对**事先明确支持的请求**执行确定性降级并标注，不得冒称模型成功分类。
- 有界线程池，建议本地默认 `maxConcurrentRuns=2`、`maxQueue=10`（可配置），队列满明确 `429/503`；不允许无限队列。
- 单机 S1 不启用公网访问，绑定 loopback、本地开发权限边界，不宣称具备真正的鉴权/多租户隔离。
- 对会话和任务内存注册表制定最低数量上限与清理规则，避免无限增长；消息集合必须线程安全。

### S0-08：冻结 Hypothesis 缺口的阶段归属（**不提前改开发顺序**）

Codex 已指出现有 Core 的 Hypothesis 语义不完整：假设可创建、可失效，但没有充分验证/实现 `SUPPORTED` 的通路；真实模型可能跳过假设直接结案。

**处理决定**：

- S0 **登记**缺口与当前测试事实，S1 **不**在没有真实业务场景的情况下大改模型/Guard；旧 A/B/C/D `RESOLVED` 保持兼容。
- 在 **S2** 增设明确的 Hypothesis 调查闭环子任务，作为进入 S3 双域专业验证的前置验收：候选假设、关联证据需求、支持/反驳、因新证据失效，以及故障因果诊断结论的可追溯关联。
- **不**一刀切要求所有任务都有 `candidateRuleId`；事实查询/设备当前配置核验并不等价于故障因果诊断。

## 3. S1：最小自然语言业务行为（本次仍然实施）

### 3.1 路由范围

| RouteDecision | 用户例子 | 处理方式 | S1 边界 |
| --- | --- | --- | --- |
| `QUERY` | “CAR-B 的出厂控制器是什么？” | 两类受限 Repository 查询，返回结构化来源 | 不替代状态重建 |
| `DIAGNOSE` | “CAR-B 控制器通信超时，帮我诊断” | Catalog + Rule 验证 → 原 Core 运行 | 仅已支持模拟领域/症状 |
| `CLARIFY` | “帮我看看这台设备”（没有当前设备） | 请求最少缺失信息 | 不凭空猜设备 |
| `UNSUPPORTED` | 未知设备、未覆盖问题或实际危险操作 | 清楚说明当前能力范围 | 不伪造结果/不控制真实设备 |

`EXPLAIN`（围绕诊断追问）和 `CONTINUE`（用户补充证据、暂停后恢复）留给 S2；S1 的 session 只支持当前设备等**有限**上下文，不承诺完整多轮诊断。

### 3.2 事实查询：修订后的真实工具契约

**不再使用初版错误的 `QueryService → CapabilityGateway.execute(DiagnosisRequest, CallCapability)` 路线。** 当前 Gateway 需要诊断 Scope，事实查询不应为了过关伪造 `symptomCode`、`asOf`。

S1 采用：

```text
TaskRouter(QUERY)
  → 校验 session/assetId，且 assetId 在受支持演示 Catalog 中
  → QueryService（仅 ASSET_PROFILE / MAINTENANCE_HISTORY）
  → AssetRepository.profile(assetId) / AssetRepository.history(assetId, null)
  → 检查返回记录资产归属、字段来源与数据性质
  → QueryAnswer（结构化 sources、实际事实、限制说明）
```

- 这是一个有明确范围的**应用层只读查询适配器**，不是让 Agent 绕过 Gateway；**所有诊断中的模型工具调用继续走 Gateway**。
- 不提供任意查询语句、路径、componentId 或恶意 JSON 作为泛化工具入口；检验返回记录 `assetId` 是否匹配。
- `ASSET_PROFILE` 表达**出厂/档案记录**，不能直接回答“目前安装的控制器肯定是什么”。
- `MAINTENANCE_HISTORY` 按实际维修/更换记录回答，不将“发生过更换”直接等同于“当前实际配置已现场确认”。
- `QueryAnswer.sources` 必须区分 `evidenceId` 与 `sourceRef`，不得把 `CAR-B-FACTORY` 填成 `sourceRef`。

建议响应形状：

```json
{
  "answer": "模拟出厂记录表明 CTRL-01 初始型号为 D-120A。",
  "scope": "FACTORY_RECORD",
  "dataNature": "SIMULATED",
  "sources": [
    {
      "evidenceId": "CAR-B-FACTORY",
      "sourceRef": "simulated:CAR-B/FACTORY",
      "sourceType": "FACTORY",
      "dataNature": "SIMULATED"
    }
  ],
  "limitations": ["此记录不代表当前现场安装配置"]
}
```

以上具体记录值需在 S0 再核对当前 fixture；只展示来源字段的示例，**禁止把响应样本当 Controller 常量答案**。

### 3.3 诊断请求：明确两种时间和受支持范围

S1 的应用层对象（可用 `record`，不必变更旧 Core）：

```text
DiagnosisGoal {
  originalUserMessage: String
  normalizedGoal: String
  assetId: String
  domain: String
  symptomText: String?
  symptomCode: String
  requestedAt: Instant
  diagnosisAsOf: Instant
  dataNature: SIMULATED
}
```

映射规则：

1. 用户自然语言由 TaskRouter 识别意图和 `assetId` 候选；设备身份必须经 Catalog 校验。
2. `SupportedScenarioCatalog` 提供对应的 `domain`、允许的 `symptomCode` 和固定 `diagnosisAsOf`。
3. 受限别名表可匹配“控制器通信超时/通信中断”等描述为候选 `COMM_TIMEOUT`，但**不是任意自然语言症状都映射到 `COMM_TIMEOUT`**。
4. `RuleRepository.query(domain, symptomCode)` 对候选规则存在性做最终检查。
5. 用已验证字段构造旧 `DiagnosisRequest(assetId, domain, symptomCode, diagnosisAsOf)`。
6. `originalUserMessage/normalizedGoal` 只保留在应用层用于追溯与响应说明；**S1 不声称已经传入 Core 并让其执行开放式自由目标调查**。
7. 没有支持的设备/故障/规则时返回 CLARIFY 或 UNSUPPORTED，不借修改 Guard 硬凑结论。

这样既交付自然语言入口，又避免因今天没有完整领域数据就实现虚假的“自由故障码诊断”。

### 3.4 最小会话：保留但不扩张为长期记忆

```
ConversationSession {
  sessionId: UUID
  currentAssetId: String?
  activeDiagnosisId: UUID?
  createdAt: Instant
  messages: bounded list<ConversationMessage>
}
```

- HTTP 先创建 session，再发送 message；明确资产时校验并记录当前 assetId。
- “这台设备”仅在已有明确 `currentAssetId` 时复用；否则 CLARIFY。
- S1 **不支持**补证写入、诊断恢复、已完成案件复杂问答与跨进程历史记忆。
- 在无身份认证的本地 Demo 中，`sessionId` 只是记录绑定/访问门槛，**不是生产级用户身份隔离**。查询 session 归属不符统一 `404`，以免探测对象是否存在。
- 需要线程安全消息追加、会话上限、单会话最大消息数和超期清理；不能用无限的 `ConcurrentHashMap + ArrayList`。
- 默认建议 `maxSessions=100`、`maxMessagesPerSession=40`、`maxStoredRuns=100`，超限拒绝创建或清理**已结束**记录；不得在仍运行时删除其内部对象。具体值可配置并实测。

### 3.5 TaskRouter：路由模型和故障诊断模型分开

TaskRouter 输入：用户当前消息 + 当前会话明确资产 + 受限支持目录（仅允许的资产/领域/故障摘要）。输出：严格 DTO `RouteDecision`。

建议处理顺序：

```text
基础入参检查（空值/长度/格式）
  → 明确 assetId / 当前 asset 上下文校验
  → 离线受限规则 Router 或在线结构化 LLM Router
  → 输出 QUERY / DIAGNOSE / CLARIFY / UNSUPPORTED
  → 程序复核 Catalog、症状映射与查询权限
  → QUERY → QueryService；DIAGNOSE → DiagnosisRunService
```

- LLM **只**建议 route、目标资产候选、queryKind、症状文本和回复要点，不产生确诊、事实与权限结论。
- Router 独立于 `StructuredReasoner` 的 `ActionProposal` 协议，使用专门 Prompt、响应 DTO、解析/重试策略。
- 离线模式可用有限、可审计的确定性映射，仅能证明**受限请求覆盖**，不能在报告中写“已验证任意中文理解”。
- 在线模式必须真实使用配置好的模型；若 Key/网络不可用，模型测试标 `BLOCKED_BY_ENV`，离线验证仍可完成。
- 模型选择和 Key/URL 只允许服务器配置；HTTP 不允许重设服务端模型提供方、`baseUrl` 或密钥。

### 3.6 异步诊断运行：每任务独立 Reasoner

```text
DiagnosisRunService.create(goal, sessionId)
  → 生成 diagnosisId，登记 executionStatus=QUEUED
  → 有界线程池提交（满载拒绝，不保留幽灵任务）
  → 在工作线程置 RUNNING
  → ReasonerFactory.create()    // 每次 Run 新建，不能 Singleton
  → TaskOrchestrator.run(validatedRequest, budget, reasoner)
  → 检查 RunReport.result().runStatus()
        COMPLETED → executionStatus=COMPLETED，保存真实 outcome 和映射
        FAILED    → executionStatus=FAILED，提取安全错误码
  → 保存可供 GET 查询的最终结果和事件
```

- HTTP POST 成功接受诊断时**固定返回 `202 Accepted`** 和 `Location: /api/diagnoses/{diagnosisId}`；响应体固定 `executionStatus="QUEUED"`。即使工作线程已瞬间完成，也不改变 POST 的语义，真实状态靠 GET 获取。
- 该固定响应反映的是“已接受”，**不是声称任务现在一定还在队列中**。
- `reasonerFactory` 每次创建 `ScriptedReasoner/OpenAiReasoner/QwenReasoner` 的独立实例；不能共享可变 `attempts` 或延迟初始化 `step`。
- 只读 Repository、注册完成后不可变 Gateway 可以依实际线程安全性共享；仍要检查隔离。
- 有界执行器拒绝任务时必须移除或标记拒绝的运行注册项并返回 `429`/`503`，不能留下永远 `QUEUED` 的 ID。
- `Future` 正常返回不代表 Core 成功；必须读取 Core 自身 `RunStatus`。
- 内部 `diagnosisId → coreTaskId/reportPath` 映射明确记录，调试日志关联公开 diagnosisId；响应不泄露绝对路径。

### 3.7 事件：今天只做结束后查询和白名单视图

当前 Core 使用的类型（需在 S0 核对当前源码）：

```text
REASON_INPUT, MODEL_ATTEMPT, ACTION_PROPOSED, CAPABILITY_RESULT,
HYPOTHESIS_INVALIDATED, RULE_SELECTION_INVALIDATED,
GUARD_RESULT, GUARD_REVIEW, STATE_COMMITTED,
TECHNICAL_FAILURE, TERMINATED
```

API 的 `RunEventView`：

```java
record RunEventView(
    int sequence,
    Instant recordedAt,
    String type,
    long stateVersion,
    String summary,
    List<String> referenceIds
) {}
```

- **不要**把原始 `RunEvent.data`、`REASON_INPUT` 的 `Reasoner.Context`、完整 Prompt、模型原始输出、私密参数或堆栈直接给前端。
- `summary/referenceIds` 从已允许字段**白名单生成**；某事件无安全可展示细节时仅返回类型和通用摘要，不能凭空生成内部动作。
- API 使用真实的 Core 事件类型；若将来定义前端聚合事件名称，必须有清晰 `CoreEvent → ViewEvent` 映射文档。
- `GET /events` 在运行中返回 `eventsAvailable=false, events=[]`；完成且有报告才返回最终事件。**不做实时推送、不添加 Event Sink**。

### 4.7 HTTP 错误契约

| 情况 | 状态码 | 说明 |
| --- | --- | --- |
| 空消息、非法 ID、长度超限 | `400` | `INVALID_REQUEST` |
| sessionId/diagnosisId 不存在或不属于该会话 | `404` | `NOT_FOUND`，不泄露他人对象存在性 |
| 已知但不支持的资产/故障 | `200` + CLARIFY/UNSUPPORTED | 业务限制，不是系统故障 |
| 有界队列满 | `429` 或 `503`（冻结一种） | `RUN_CAPACITY_EXCEEDED`，无幽灵任务 |
| Router 依赖模型失败 | `503` 或业务明确的受限降级 | 不冒充已完成 LLM 识别 |
| 异步 Core 模型失败 | GET 返回 `FAILED` | 不能转成 `NEED_EVIDENCE` |
| 内部未预期错误 | `500` | 安全错误码 + requestId，不回显栈/密钥 |

统一错误响应至少包括 `code/message/requestId`。S1 无真实认证，因此仅用于 loopback Demo，sessionId **不能**被当成生产级身份凭据。

## 8. Windows / PowerShell 验收操作示例

所有命令按**真实项目 `pom.xml` 和端口配置**核对；下面是开发期建议，执行结果以本机为准。

```powershell
# 0. 确保运行环境是项目 README 指定的 JDK 21
java -version
mvn -version
mvn test
mvn package

# 1. 旧 CLI 回归（真实 Jar 名以项目为准）
java -jar target/devicetruth-core-0.1.0.jar --scenario=B --reasoner=scripted

# 2. 在另一个终端启动 Server（S0 必须验证 Maven 插件支持的精确参数）
# 示例：mvn spring-boot:run -Dspring-boot.run.main-class=io.devicetruth.server.DeviceTruthServerApplication
# 若当前插件不支持该命令，由 Codex 提供并记录等价的实际可执行命令

# 3. 建会话
$session = Invoke-RestMethod -Method Post `
  -Uri 'http://127.0.0.1:8080/api/sessions' `
  -ContentType 'application/json; charset=utf-8' -Body '{}'

# 4. 发送自然语言诊断；成功诊断路由应对应 202 Accepted
$body = @{content='CAR-B 控制器通信超时，帮我调查'; assetId='CAR-B'} | ConvertTo-Json
$resp = Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:8080/api/sessions/$($session.sessionId)/messages" `
  -ContentType 'application/json; charset=utf-8' -Body $body
$resp

# 5. 查询实际状态与最终事件；S1 的事件只在任务结束后可用
if ($resp.diagnosisId) {
  $id = $resp.diagnosisId
  $sid = $session.sessionId
  Invoke-RestMethod -Uri "http://127.0.0.1:8080/api/diagnoses/$id`?sessionId=$sid"
  Invoke-RestMethod -Uri "http://127.0.0.1:8080/api/diagnoses/$id/events`?sessionId=$sid"
}
```

对于 `QUERY`/`CLARIFY`/`UNSUPPORTED`，统一消息接口可返回 `200 OK` 且无 diagnosisId，不应执行诊断轮询。

## 9. 风险、边界与最小防护

| 风险 | 后果 | S0/S1 处理 |
| --- | --- | --- |
| 把提交 HTTP 的时间作为业务 asOf | CAR-B 现场确认过期、误判 | 分离 requestedAt/diagnosisAsOf，使用 Catalog 历史时间 |
| 假设 Repository 存在 `domainOf/listSymptoms` | 编译失败、接口空转 | Catalog 最小演示映射，RuleRepository 精确 query |
| 普通 QUERY 假造 DiagnosisRequest 访问 Gateway | 查询语义错误 | 应用层受限只读 Repository 访问，诊断 Gateway 不变 |
| CLI/Web 共用现有 Main 生命周期 | CLI 卡住或 Web 退出 | 两 Main、显式 Maven 主类、启动验证 |
| 共享一个在线 Reasoner | `attempts` 混合、竞争初始化 | 每任务 ReasonerFactory.create() |
| API ID、Core ID、报告 ID 混淆 | 无法关联证据与事件 | diagnosisId 主键 + 内部映射 |
| Core 返回失败但 Future 正常结束 | 错将 FAILED 标记完成 | 读取 `report.result().runStatus()` |
| POST 返回瞬态 RUNNING/COMPLETED | API 竞态、测试不稳定 | 诊断接收固定 `202 + QUEUED` |
| 运行中宣称能看事件 | 界面和事实不一致 | S1 只结束后读取，明确 eventsAvailable |
| API 返回 RunEvent.data 原文 | 泄露模型上下文/敏感证据 | 白名单 RunEventView |
| `sourceRef` 误填 evidence ID | 证据溯源错误 | 结构化 sources 同时返回 ID、Ref、类型 |
| 伪称真实设备数据 | 比赛演示误导 | 明确 `SIMULATED`、历史时间点 |
| 会话/任务无限缓存 | 内存泄漏与串案 | 有界、线程安全、超期清理，不删运行中记录 |
| Session UUID 被当作正式鉴权 | 可枚举/泄露使用者数据 | loopback Demo 限制，明确无认证；后续再做权限 |
| 为产品壳忽略 Hypothesis 缺口 | 创新主张无法验证 | S2 明确设置 Hypothesis 验收，不提前扰乱 S1 |
| 为求 S1 快速通过降低 Guard | 错误/危险结论 | Core 既有验证与安全负例全部回归 |
