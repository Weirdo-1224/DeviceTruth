**注意**：目标路径如果已存在同名文件，请先用 diff 比较并备份；不要直接覆盖已有 `spec.md/task.md/state.md` 或用户修改。

## 2. 推荐执行顺序

1. 首先将本包放到仓库，**保留旧 V0.1 文档和源码**。
2. 启动 **R01 DeepSeek 只读审计会话**：用 `prompts/DEEPSEEK_START.md`，只核对源码、测试和历史基线，填写 `S0_AUDIT.md`。Codex 独立 Review，写 `reviews/R01.md`。
3. 启动 **R02 DeepSeek 契约确认会话**：以 R01 事实修改、冻结 `spec.md` 与任务计划（只改文档），Codex Review；用户对重大架构取舍做最终批准。
4. 运行 **R03~R06 DeepSeek 开发会话**：一会话一个任务，先测试再审查；Codex 逐轮复审本次 diff，必要时返回修复。
5. 运行 **R07 集成验收会话**：按原方案 TC-01~TC-20 对照执行；留下真正命令、退出码、请求/响应和失败记录。

> 此处 R01/R02 用 DeepSeek 负责审计资料和文档草案，Codex 独立核查，以保证**每个会话都能由另一个模型 Review**。如果你更想让 Codex 主持 S0，也可以让 Codex 先形成审计报告，再由 DeepSeek 复核；但不建议 Codex 把自己的审计当作独立 Review。

## 3. 单个会话标准流程

`读取项目状态 → 确定任务 ID → 只做当前任务 → 实际运行测试 → 交付摘要 → Codex 独立 Review → 修复/复审 → 通过后更新状态 → 换会话`

- DeepSeek：改源码 / 写测试 / 运行命令。仅对 R01/R02 允许写审计和规格文档，**不进行业务编码**。
- Codex：原则上**不改源码和测试**，可以新建 `reviews/Rxx.md`。审核 `PASS` 后可维护 `state.md/task.md` 的状态项；涉及 `spec.md` 变化须得到用户批准并有证据。
- 用户：决定重大架构分歧；不让两个模型自行“改出第三套方案”。
- 每轮通过条件：当前任务的验收点有真实测试证据，Codex 没有未解决的 P0/P1，相关旧测试未退化或已经如实记录阻塞。

### Git 规范

- 在 S0 首先记录原始 `git status`、当前分支与基线 commit；不得 `reset --hard`/`clean -fd` 或覆盖未跟踪文件。
- 不假设仓库已有干净工作树。Review 比较“本轮开始基线 → 本轮交付修改”，而不是无差别扫描所有历史改动。
- 没有明确授权时，模型不得创建 commit、tag、push、改远程分支。可以提出建议，交由用户决定。
- Review 中建议检查当前 diff、关键调用链及关联测试，不要求每次重读全仓库。

## 4. 优质生成/迭代方式

**不要一次性让模型读修订方案就直接生成所有代码。** 最稳妥的方式是本包作为 v0，按以下闭环迭代：

1. **设计规格来自方案**：预先明确 S0/S1 边界、契约、依赖和测试点。
2. **源码事实来自 R01**：把方案中“据历史审查”的描述逐一核查，引用实际类/方法/文件和测试结果。
3. **契约冻结来自 R02**：Codex 把关是否存在与当前仓库矛盾、隐性重构、不可验收项。
4. **每轮代码来自小任务**：让 DeepSeek 在受控范围内实现，不扩大到 S2/S3/S4。
5. **Review 必须来自代码和实际测试**：不能只依赖 DeepSeek 的工作摘要或自述通过数量。

这样生成的包质量会明显高于“让 AI 一口气规划、写代码、验收并自行宣布完成”。

## 5. 关键边界（不得混淆）

- `CAR-B / COMM_TIMEOUT` 是**汽车演示数据**，**不是**工业 `SC-0245-B`。
- CLI 的真实场景为 **A/B/C/D**；E 是负例测试，不是 `--scenario=E`。
- 42 项通过是**历史报告**，不是今天的新测试结果。
- `diagnosisAsOf` 是模拟业务时间，不等于 HTTP 请求时间 `requestedAt`。
- S1 QUERY 仅 `ASSET_PROFILE` / `MAINTENANCE_HISTORY`；诊断仍进已有 `TaskOrchestrator` 和 `CapabilityGateway`。
- POST 诊断固定 `202 + QUEUED + Location`；真实结果/事件通过 GET 读取。
- S1 不做实时 SSE、可恢复补证、标准 SKILL.md、工业双域、Vue、数据库持久化、完整 Hypothesis 调查闭环。

## 6. 如果一天内做不完

允许以 `R03/R04/R05...` 的**已通过会话**为停止点；在 `state.md` 记录未完成内容和测试事实。**不要为了赶进度把未运行的在线 LLM 验证标为 PASS。**
