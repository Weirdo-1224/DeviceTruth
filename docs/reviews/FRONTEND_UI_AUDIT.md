## 1. 技术架构与真实运行链路

- `frontend/package.json`：Vue 3.5.45、TypeScript 5.9.3、Vite 8.3.7，插件 `@vitejs/plugin-vue` 6.0.10；Vitest 5.1.0、vue-tsc 3.3.14。仅 Vue 是运行依赖；未声明 UI 组件库、图标、图表、动画、路由或状态管理库。版本取自 package.json，未将间接依赖当成产品选型。
- `frontend/src/main.ts:1` 直接挂载 `App.vue`，无前端路由；`App.vue:31` 使用 ref/computed/watch 管理会话、资产、消息、运行状态和输入，localStorage 只记最近会话 ID（`:199`）。当前是单页多个业务区域，不是多个实际路由页面。
- CSS 主要是各 Vue 文件的 scoped 原生 CSS，无 Tailwind、SCSS、CSS Modules 或统一 token 文件。颜色、字号、圆角等直接写值；存在部分相近而重复的 hint/error/badge 样式。父组件的 scoped 样式对直接子组件根元素可生效，因此 `card` 的视觉也依赖父子边界；抽组件时要核对。
- `frontend/src/api.ts:191` 封装 fetch，定义请求、类型与错误；`:334` 原生 EventSource，`timeline.ts:45` 管理事件视图，seq 去重、断线重连与历史读取；`:495` 轮询 run 作为补充及终态校准，`:426` 轮询文件。没有发现 WebSocket。`frontend/vite.config.ts` 开发时 `/api` 代理 8080。
- 用户输入经 `App.vue:245` 发消息，API 返回 run 后 `track` 轮询；watch 跟随时间线，补答带追问关联，终态显示 `DiagnosisReport`。选择资产后 `EvidenceComparison` 独立读取资产；上传 Markdown 后等待解析，成功文件作为下一条消息附件。重构需保留这些连接，不把显示状态当成服务端事实。

## 3. UI/UX 问题（严重程度为改造优先级，非线上故障定级）

1. **P1 工作流层级弱。** `App.vue:365-446` 顺序放状态、时间线、资产、上传、消息、追问、报告、输入；对话和输入被多个区域分隔，输入在长报告之后。源码确认顺序；滚动距离和用户效率需实机验证。建议对话为主，调查过程和证据按需展开，追问与输入保持明显关联。
2. **P1 可信信息关联弱。** `DiagnosisReport.vue:83-134` 事实只显示截短引用 ID，引用列表的按钮单独展开原文；事实上的 ID 是文本而非直接跳转。用户需自行匹配，尤其多引用时。保留来源版本、核实级别和安全提示，并让事实可定位来源；不添加伪造的可信度分数。
3. **P1 实时状态可能误导。** `RunTimeline.vue:120` 仅按 `live` 二分“实时/已结束”；`App.vue:77` 明确存在非 live 且无终态的情况，断线/恢复时可能被显示为已结束。需浏览器模拟断网验证实际出现条件，设计应区分连接中、重连、终态。
4. **P2 缺少自适应布局规则。** `App.vue:455,487,492` 最大宽 1024px、220px 固定历史栏且未见媒体查询；`EvidenceComparison.vue:100,148` 六列表格无专门的横向滚动容器。大屏空白、窄屏挤压或溢出是合理风险，具体表现待 1440×900、1920×1080 和窄屏截图验证。
5. **P2 信息密度与术语。** `RunTimeline.vue:58-112` 展示工具名、模型、原始 outcome 和 token；`DiagnosisReport.vue:74` 直接显示 category/risk/dataNature 枚举。对检修人员可读性依赖技术背景；建议默认显示可理解的状态与结果，技术细节可展开，保留原始值供核查。
6. **P2 样式体系松散。** 卡片、圆角、色彩和 12–16px 字号散布三个组件及 App；按钮以原生控件和链接混用，缺统一交互态规范。`App.vue:609` 通用按钮与 `.link` 规则共存，应验证 disabled 与焦点实际效果；不是宣称所有控件不可访问。
7. **P2 历史定位弱。** `App.vue:345-357` 会话仅按更新时间命名，缺问题摘要及状态，长列表难识别；搜索、分组或标题需先确认数据和业务需求。
8. **P2 上传与反馈有限。** `App.vue:398-406` 展示上传/解析状态与原始失败码；`api.ts:422` 虽有 retryFile，当前 App 未接重试按钮。空消息、失败与等待有文本，但没有统一恢复动作；是否需要新增后端能力应另行确认。
9. **P3 证据表格强调方式有限。** `EvidenceComparison.vue:107-125` 冲突按行背景显示并附总状态文字，来源、核验、时点信息可见，但复杂冲突缺聚焦摘要；不应仅凭颜色表达状态。

视觉方向上已有蓝色主色、灰色文本和状态色，不能说完全没有一致性；缺的是有命名、层级和使用规则的系统。字体使用系统字体、中文微软雅黑回退，行高 1.6；实际对比度、字号舒适度、键盘焦点、读屏、文本缩放、动画偏好以及真实屏幕溢出均未验证。

## 4. 组件复用与保护边界

已有三项业务组件：`RunTimeline.vue`、`DiagnosisReport.vue`、`EvidenceComparison.vue`；没有独立基础按钮、表单、弹窗或设计 token。报告组件以 props/emit 展示为主，适合先设计；资产组件自身 fetch/watch，展示与数据获取耦合；App 同时处理 API、轮询、恢复、上传、消息与排版，拆分时容易引入竞态。重复样式可归纳为 token 和小型基础组件，但勿为了组件化重写所有逻辑。

**保留** `api.ts` 契约、`timeline.ts` 序号与生命周期、追问三元组、请求键、切换会话隔离、取消与终态判定、后端安全/引用约束。**可重构** 布局、文案映射、样式和视图组件边界，以现有状态为输入；保持来源、风险、数据性质和不确定性可见。**暂不建议动** 后端协议、EventSource 重连机制、业务状态机和数据真实性语义。全局 reset、按钮/表格/字体规则可能影响所有 Vue 组件及同域旧演示入口，需限定挂载范围、检查 scoped 根节点与原生控件。

## 5. 方案对比（粗估，1 名前端熟悉项目、工作日；不含产品确认和后端新增，需先做原型校准）

| 方案 | 实施及兼容性 | 优点 / 缺点 | 改动、耗时、风险与适用条件 |
|---|---|---|---|
| A 保留体系 | Vue 原生 CSS 变量+少量基础组件，逐区域替换 | 依赖少、贴近现有代码；无障碍和复杂组件须自行维护 | 中，首阶段约 5–8 人日；适合现有简单控件；风险是设计细节不统一，需明确规范和视觉回归 |
| B 按需引库 | Vue/Vite 可接 shadcn-vue；按需复制组件并引入 Tailwind 等 | 基础交互和可定制性较好；引入构建、样式与维护成本 | 中高，试点额外约 3–6 人日；复杂弹窗、菜单增多时适用；需评估样式冲突、键盘交互和依赖。Nuxt UI 也支持 Vue/Vite，需单独验证集成，不意味着必须迁移 Nuxt |

| D Skill+浏览器反馈 | 明确设计规范、固定样本和视口，分小批实现、截图比对、键盘及流程回归 | 能持续发现视觉与交互问题；需维护环境、稳定数据和人工审美判断 | 首次搭建约 2–4 人日，迭代另计；适合本项目。截图不能替代 SSE、业务与安全测试 |

## 6. 设计方向与信息架构建议

以「可信调查工作台」为中心：克制的中性色背景、清晰蓝色主操作、带文字的状态色；建立语义化颜色、间距、字号、圆角、边框和焦点 token。避免深色炫技、无意义统计卡片和不可解释的置信百分比。优先展示当前问题、等待用户的动作、结论与安全边界；工具与模型技术日志作为可展开的调查记录。

建议桌面布局：左侧会话导航；中央对话、追问与持续可见的输入；右侧可折叠的调查/证据面板，包含运行状态、来源及所选设备事实。报告在对话流中有清晰入口，展开后区分事实、资料支持、可能原因、人工核验和建议；点击事实引用直达来源和版本。冲突展示相互矛盾的原始记录、时点、来源及核实状态，不用 UI 推断哪条为真。窄屏将侧栏改为抽屉或分段，保留键盘可达和阅读顺序。独立知识库、资产及设置导航仅作为未来产品决策，不冒充现有功能或首阶段交付。

## 7. 分阶段路线与验收

1. **基线与设计确认（约 2–3 人日）**：以固定模拟数据记录空、运行、追问、完成、失败、取消、断线、冲突及长文本；1440×900、1920×1080 和 375/768 宽截图，确认 token、布局及状态文案。验收：每个截图可复现，证据标注模拟/真实；人工确认方向。
2. **工作台最小切片（约 5–8 人日）**：重排会话、消息、输入、追问、运行摘要及报告入口；保留原接口和状态机，提取有限基础样式。验收：新会话→发送→运行→补答→完成→引用展开、取消、刷新恢复和切换会话均通过；断线重连 seq 不重复；小屏无关键内容遮挡，键盘可完成关键操作。
3. **可信报告与资产对照（约 4–7 人日）**：事实关联来源、风险层级、冲突和时点可读性。验收：事实/可能性/现场核验分明，引用版本与原文一致，安全提示不可被折叠隐藏；无资产不产生已确诊视觉暗示。
4. **资料与历史完善（约 3–5 人日）**：优化上传反馈、历史识别和错误恢复；不虚构管理功能。验收：解析中/成功/失败、长历史、空状态清晰，附件关联与旧会话恢复不回归。所有估时是规划假设，不是承诺；在线模型、真实 PG 和模拟测试分别记录。

回归建议：`cd frontend && npm run test -- --run`、`npm run build`；已有浏览器 SSE 场景及相关后端测试按实际环境执行，另测断网重连、追问、重复提交、切换会话、上传失败、来源展开和移动端。浏览器截图比较需固定视口、字体、数据和时间；不因截图通过而宣称真实模型或现场验收通过。

## 8. 优先对象与第一阶段范围

严格说当前没有三个独立页面，优先的三个**区域**是：① Agent 对话与追问工作台，决定主路径；② 运行时间线，决定调查透明度和状态信任；③ 诊断报告与引用，决定结论可追溯性。资产对照紧随其后。第一阶段最小范围仅完成工作台布局、会话导航、对话/输入/追问及运行摘要的视觉重排，保留现有报告和资产功能并保证可达，不新增 CRUD、图表、后端接口或组件库。先确认设计稿和状态清单，再开始实施；本报告不是实施授权。
